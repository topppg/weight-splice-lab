# weight-splice-lab harness audit (2026-11-06)

Scope: `src/weight_splice_lab/harness/*`, `toy/*` as used by the harness, `experiments/phase3/run_editor.py`,
`overnight.sh`, `gpu.py`, `memwatch.py`. No tracked file was modified. Scratch tests are in this directory
(`t1_units.py` … `t6_refusal_usage.py`), all CPU-only, on a tiny model or the real 20 MB base, with peak RSS
well under 1 GB. Nothing was left running: every probe was followed by a `pgrep` check.

Severity: **critical** = can silently invalidate published results or the machine; **major** = loses or
biases runs or breaks a stated guarantee; **minor** = edge case or inaccuracy.

---

## Critical

### C1. The unsandboxed driver follows symlinks the editor creates in `work/`, so the editor can read any file into its prompt and write outside the sandbox
- **Where:** `driver.py:156-160` (handoff reads `work/notes.md`), `driver.py:299-300` (appends every cell to
  `work/cells.py`), `driver.py:433-435` (`mirror` copies `work/notes.md` into the repo with `copy2`),
  `forward.py:189-190, 244-248, 270, 273` (writes `fwd_k.jsonl`, `fwd_k/<model>/*.npy`, `meta.json`),
  `edit.py:44-55` (reads `work/edited/**`). Sandbox profile: `kernel.py:34-45`.
- **Scenario:** the kernel may create files in `work/`, and symlinks count as file creation there. In one
  cell the editor runs `os.remove('work/notes.md'); os.symlink('<repo>/docs/phase2-toy.md', 'work/notes.md')`.
  At the next handoff the driver, which runs outside the sandbox, reads the target and puts its last
  8,000 characters into the editor's prompt. That leaks the reference splice or the hidden-eval code. `mirror`
  then copies the file into `runs/phase3/<id>/notes.md`, which gets committed. In the other direction,
  `work/cells.py` pointed at a `.pth` file in a site-packages directory makes the driver append the next
  cell's code there, which the next unsandboxed `uv run` would execute. A `work/fwd_k.jsonl` pointed at any
  user file lets the driver overwrite it.
- **Verified by test** (`t2_kernel_driver.py`, K1): reading the canary file directly from the kernel is
  denied (`PermissionError`). The symlink is created. `_handoff_text` contains the canary. The driver created
  and appended to `canary/appended.pth` outside the sandbox. The audit flags this only when the code contains
  a literal absolute path: `os.symlink(chr(47)+'Users', …)` is not flagged (`t1_units.py`).
- **Fix:** (1) In the SBPL profile, add `(deny file-write-create (vnode-type SYMLINK))` (and hard links:
  `file-link`). (2) In the driver, never follow links under `work/`: open with `O_NOFOLLOW`, or reject a
  path if `p.is_symlink()` or `p.resolve()` is not under `work/`. Write forward outputs to a driver-owned
  temp file, then `os.replace` it into `work/`. (3) Before each handoff or save, scan `work/` for links and
  stop the run (`isolation:`) if any are found.

### C2. Nothing stops the kernel from using the GPU (MPS or MLX), and the memory guard cannot see GPU memory
- **Where:** `kernel.py:34-45` (`(allow default)`: IOKit and Metal are allowed), `kernel_server.py`
  PRELUDE (MPS is not disabled), `kernel.py:98-106` (the guard measures RSS only). `mlx` is installed in the
  venv the kernel uses.
- **Scenario:** to speed up a large SVD or least-squares solve, the editor runs `torch.linalg.svd(x.to('mps'))`
  or `import mlx.core`. The task says "CPU only", but nothing enforces it. MPS/Metal allocations live in
  unified GPU memory and do not show up in the process RSS that `Kernel._rss_gb` polls, so the 2 GB limit
  never trips. memwatch is the only backstop (see M7). This is the failure mode that already froze this Mac.
- **Verified by reading.** Not tested on purpose, because testing it means touching the GPU.
- **Fix:** In the profile, deny GPU access, e.g. `(deny iokit-open (iokit-user-client-class "AGXDeviceUserClient"
  "IOSurfaceRootUserClient"))` and `(deny mach-lookup (global-name "com.apple.MTLCompilerService"))`.
  Check it with a kernel test asserting `torch.backends.mps.is_available() is False`. Also set
  `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.0` in the kernel env. Measure footprint with `phys_footprint` rather
  than RSS.

## Major: experimental validity

### M1. The kernel's rules can be bypassed, including running the full model in the kernel; the audit only flags it
- **Where:** `kernel_server.py:84-96` (patches live only on objects already imported), `34-35`
  (`torch._C._set_grad_enabled` is untouched).
- **Scenarios (all verified by test, `t3_bypass.py`, `t3b_reimport.py`, `t2_kernel_driver.py` K2):**
  - `del sys.modules['model']; import model as m2` gives a fresh, unpatched `ToyLM`. `net(x, capture={})`
    takes the manual-attention path, which avoids the patched SDPA, and returns logits. **The full model runs
    inside the kernel.** Audit result: one `flag` (on `load_state_dict`) and no violation. Copying weights
    with `p.copy_` instead would raise nothing at all.
  - `torch._C._set_grad_enabled(True)`, a tensor with `requires_grad=True`, and
    `torch.autograd.Variable._execution_engine.run_backward(...)` return a real gradient
    (`tensor([-2.,-2.,-2.])`). The audit catches this only because the literal names appear in the code.
  - Deleting the `torch.optim*` entries from `sys.modules` and re-importing gives the real `torch.optim.SGD`.
  - `torch.ops.aten.scaled_dot_product_attention` works.
  - A failed grad attempt can leave grad mode enabled for later cells.
- **Impact:** the claim "model execution blocked (3 ways)" is much weaker than written. A run that broke
  rule (b) would show 0 violations.
- **Fix:** after every cell, have the kernel check and report runtime invariants (store them in
  `tool_calls.jsonl` and treat any change as a violation):
  - `torch.is_grad_enabled()` is False;
  - `sys.modules['model'] is toy_model`, and each class's `forward` is still the forbidder;
  - every `torch.optim*` entry in `sys.modules` is still `_Forbidden`;
  - no live tensor in the namespace has `requires_grad` or a non-CPU device.

  Also delete `model.py` from `sys.path` after the import, and keep the source readable only as text.

### M2. The audit has false negatives, starting with a `#` anywhere on a line
- **Where:** `audit.py:41` (`line.split("#", 1)[0]`), `audit.py:8-29`, and the output scan, which sees only
  the first 10k characters (`driver.py:293`).
- **Scenario (verified by test, `t1_units.py`):** `x = "#"; torch.optim.SGD([w], lr=0.1)` gives **no hit**,
  because everything after the `#` inside the string is dropped. These patterns are also not flagged at all:
  - `del sys.modules[...]`;
  - `runpy.run_path('model/model.py')`;
  - `exec(Path(...).read_text())`;
  - `exec(base64.b64decode(...))`;
  - `from torch import autograd as ag; ag.Variable._execution_engine`;
  - `t.requires_grad = 1`;
  - `getattr(torch, 'opt'+'im')`;
  - `loss.grad_fn(...)`.

  A `HarnessRuleError` caught by the editor's own `try/except` leaves no trace in the output either.
- **Fix:** strip comments with `tokenize` rather than `split('#')`. Add flags for `sys.modules`, `runpy`,
  `exec(`, `eval(`, `compile(`, `__import__`, `getattr(torch`, `base64`, `_C\.`, `grad_fn`, `_execution_engine`,
  `symlink` and `requires_grad\s*=`. Scan the full output rather than the cut one. Rely mainly on the runtime
  invariants from M1, because regexes cannot be complete.

### M3. Results carry no provenance, and the overnight chain can change the code between pilots
- **Where:** `driver.py:402-415` (`result.json` has no git SHA, dirty flag or harness version) and
  `overnight.sh:28` (`git pull --rebase` after each pilot, before the next one runs).
- **Scenario:** pilot2 finishes, and `publish` pulls `origin/main`, which already holds the v2 usage fix
  (`558981f`). pilot3 then runs different driver code than pilot2, and neither `result.json` records which.
  The LOGBOOK already says v1 and v2 runs differ ("future runs are a new harness version"), but nothing in
  the artefacts tells them apart.
- **Verified by reading.**
- **Fix:** write `git rev-parse HEAD`, `git status --porcelain` and a hash of `harness/` and `prompts/` into
  `config.json` and `result.json` at launch. Refuse to start when the tree is dirty, or record the diff. In
  `overnight.sh`, pin the commit for the whole chain (no pull before the last pilot ends).

## Major: robustness of unattended runs

### M4. A crash skips `finalize` entirely: no hidden eval, no audit, nothing mirrored, while a release is still uploaded
- **Where:** `run_editor.py:71-72` (`driver.run` then `finalize`, with no try/finally) and `overnight.sh:29, 33-46`.
- **Scenario:** any exception escaping `Driver.run` (see M5), or a memwatch SIGKILL, ends the process before
  `finalize`. The state stays in `~/wsl-runs`, but `runs/phase3/<id>` is never created. Then `git add`
  fails, so nothing is committed, and the failure is not logged clearly. `publish` still uploads the latest
  manifest's edit as `checkpoints-<id>` "final edit", so the release has no matching eval.
- **Verified by reading**, plus test for the exception sources in M5.
- **Fix:** wrap the run in `try/finally`, and always call `finalize` with `stop_reason="crash: <exc>"`. Catch
  errors in `finalize` itself, so the audit and mirror still happen if the eval fails. Add a separate
  `finalize_only.py <run_id>` that rebuilds `RunState` from `state.json`, for runs killed by memwatch. In
  `overnight.sh`, skip the release when `result.json` is missing.

### M5. Ordinary editor actions raise exceptions the driver does not catch, ending the run
- **Where:** `driver.py:358` (catches only EditError/ValueError/TypeError/OSError/RuntimeError),
  `driver.py:319` (catches only ForwardError/ValueError/KeyError/TypeError), `kernel.py:121, 132` (does not
  catch a bad protocol line), `kernel.py:140` (a restart that fails raises RuntimeError).
- **Scenarios (all verified by test):**
  - The editor writes `torch.save(np_array, 'work/edited/tensors/X.pt')` directly: `save_edit` raises
    `_pickle.UnpicklingError`, which is uncaught. A garbage file does the same. An **empty** `.pt` raises
    `EOFError`, which is uncaught. An empty file is also what is left if the kernel is killed mid-`torch.save`
    by the time or memory limit. (`t4_staged.py`)
  - A background thread prints after its cell returns (a progress print or a library warning). The line
    goes to the kernel's protocol pipe, because fd 1 is restored to it, so the next `Kernel.run` raises
    `JSONDecodeError`. (`t5_stray_stdout.py`)
  - `work/fwd_k` exists as a file and the editor asks for a teacher-forced pass: `NotADirectoryError` (an
    OSError, which `_forward` does not catch) propagates. (`t2_kernel_driver.py` K3)
- **Fix:** in each tool handler, catch `Exception`, log the traceback privately, and return "the tool
  failed and was not counted". For the kernel protocol, use a dedicated pipe fd that is not fd 1, with a
  per-request nonce, and skip lines that are not JSON or have the wrong nonce.

### M6. Rate-limit wording and "rate_limits" keys end the run as a usage limit instead of backing off; a timeout leaves Codex running
- **Where:** `codex.py:171-175`, `driver.py:237-239` (`limit_hit` is checked before throttling) and
  `codex.py:189-203` (`subprocess.run(timeout=)` kills only `codex-switch`).
- **Scenario A (verified by test, `t1_units.py`, `t2` K4b):**
  - A transient `429 Too Many Requests: Rate limit reached` gives `limit_hit=True`, so the run stops with
    "codex usage limit".
  - So does any error event whose JSON has a `rate_limits` key (the substring "rate_limit" matches).
  - The back-off added in `417c8c1` and `3ad8387` never runs for these.
- **Scenario B (mechanism verified by test, symptom seen in real logs):**
  - On a timeout, only the direct child is killed. A test with `sh -c 'sleep …'` showed the grandchild
    surviving.
  - pilot3 `t019` timed out at 3600 s, and `t020` and `t021`, 35 s later, failed with "thread … already
    has an active writer". The old Codex process was still alive.
  - With the current code, each retry is classed as throttled and burns a turn.
  - If the orphan finishes its turn later, the thread gets a reply that was never parsed, and the driver
    then resends the same message, which duplicates a turn. Its tokens and points are never recorded per turn.
- **Fix:**
  - Classify errors on the `message` text only, not the JSON dump.
  - Treat `429` and "rate limit reached" as throttling. Stop only on explicit quota wording, such as "usage
    limit" or "hit your usage limit".
  - Start Codex with `start_new_session=True`, and on timeout `os.killpg` the whole group, then wait until
    the rollout's writer lock is gone before retrying.

### M7. memwatch is blind when it is needed most
- **Where:** `memwatch.py:76-89`.
- **Scenario:** each poll forks `sysctl` (`pressure_level`) *before* any kill decision. Under heavy memory
  pressure, `fork`/`exec` can fail or stall (ENOMEM/EAGAIN, or slow page-ins). The exception goes to
  `except Exception: log(...)`, which skips the `available < 2.5 GB` check that does not need the subprocess
  at all. memwatch keeps logging "poll error" while the machine sinks. The `psutil.process_iter`, `cmdline()`
  and `exe()` scan of every process every 0.5 s is also slow under pressure.
- **Verified by reading.**
- **Fix:** read the pressure level in-process (`ctypes` `sysctlbyname("kern.memorystatus_vm_pressure_level")`).
  Evaluate the available-memory check first and on its own, each check in its own `try`. Cache the PID list
  of repo processes and refresh it every few seconds.

### M8. The kernel's detached children survive the kill and escape the memory accounting
- **Where:** `kernel.py:98-106, 145-152`.
- **Scenario (verified by test, K6):** a cell runs `subprocess.Popen([...], start_new_session=True)`, or
  double-forks. `kernel.close()` (`killpg`) leaves it running: the PID was still alive after close, and I
  killed it myself. Once it is re-parented to launchd, `children(recursive=True)` no longer counts its RSS.
  If it is not the venv python (e.g. `/bin/dd` or `/usr/bin/python3`), memwatch does not see it either. A
  long job can therefore outlive the 900 s limit and the run itself.
- **Fix:** in the profile, deny `process-exec` except the venv interpreter, or deny `process-fork` outright,
  because the kernel needs no children. Otherwise, record descendants at every poll and kill them all on
  restart and close.

### M9. `(allow default)` leaves other routes out of the sandbox
- **Where:** `kernel.py:35`.
- **Scenario:** a cell writes `work/x.command` and runs `/usr/bin/open work/x.command`, or `osascript`.
  LaunchServices, which is outside the sandbox, runs it in Terminal with full user rights: reading the repo,
  network access, writing anywhere. The audit flags it only because of `subprocess` or `os.system` in
  the code.
- **Verified by reading.** Not tested, because it would launch apps on the user's Mac.
- **Fix:** switch to `(deny default)` with an explicit allow-list. At minimum, deny `process-exec` except
  python, and deny `mach-lookup` for `com.apple.coreservices.launchservicesd` and `com.apple.coreservices.appleevents`.

## Minor

### m1. A refusal on the first turn of a new thread leaves stale per-thread state
- **Where:** `driver.py:245, 209-212`.
- **Scenario (verified by test, `t6_refusal_usage.py`, `t2` K4):**
  - After a handoff, the first turn is refused but returns a thread ID. `st.thread_usage` still holds the old
    thread's cumulative total.
  - The next turn's delta is clamped to 0, so that turn goes uncounted (35k counted vs 50k true) and
    `last_input_tokens=0`.
  - If the handoff had been triggered by tokens, the stale `last_input_tokens` fires a **second** handoff
    straight away (handoffs=2).
- **Fix:** whenever `thread_id` changes, reset `thread_usage=Usage()` and `last_input_tokens=0`.

### m2. Failed, throttled and refused turns use up the 200-turn cap
- **Where:** `driver.py:184-190`, `budget.py:147`.
- **Scenario:** a network outage, with 7 throttle retries and 2 failures, takes up to 9 of the editor's 200
  replies. pilot2 ended on the turn cap and was evaluated on an unfinished edit, so lost turns directly change
  outcomes, and they vary between runs.
- **Verified by reading.**
- **Fix:** count only turns that delivered a model reply toward `max_turns`, and keep a separate cap on
  failed attempts.

### m3. If the kernel dies between cells, it restarts silently
- **Where:** `kernel.py:125-126`.
- **Scenario (verified by test, K5):** memwatch or an OOM kills the kernel while it is idle. The next
  `run()` restarts it and returns `restart=None`. The editor sees `NameError` with no notice that its
  variables are gone, though the prompt promises one.
- **Fix:** return a restart reason (`"the kernel had exited"`) when `start()` is called from `run()`.

### m4. Parser edge cases
- **Where:** `protocol.py:6-7, 33-35`, `codex.py:136`.
- **Verified by test (`t1_units.py`):**
  - A bare ```` ``` ```` line inside a triple-quoted string truncates the python block (body becomes
    `notes = """`). This is likely when writing markdown into `notes.md`, which the prompt asks for.
  - ```` ```py ````, ```` ```json ```` and 4-backtick fences are not recognised, so they get a nudge.
  - Only the *last* `agent_message` of a turn is parsed; a block in an earlier message is lost.
- **Fix:**
  - Close a block only on a fence whose indentation equals the opener's, or with matching fence length (CommonMark).
  - Accept `py` as `python`.
  - Parse all agent messages in order.

### m5. The practice grader is more lenient than the hidden eval when special tokens are emitted
- **Where:** `forward.py:79-83` vs `metrics.py:86-88`, `data.py:41-42`.
- **Scenario:** an edited model emits `<unk>` then `5481` for the answer `5481`. The forward tool generates
  N+2 tokens, decode drops `<unk>`, and the prefix matches, so it is graded correct. The eval generates N+1
  tokens, giving `548`, so it is wrong. The tool's claim "same criteria as the hidden evaluation" therefore
  does not hold in this case.
- **Verified by reading.**
- **Fix:** grade on token IDs, using the first N+1 generated IDs, in both places.

### m6. The scalar-multiple refusal is trivial to bypass, and zeroing a tensor is refused
- **Where:** `edit.py:76-83`.
- **Scenario (verified by test):** `2*W` is refused, but `2*W` with one entry changed by 1e-3 is accepted.
  `zeros_like(W)` is refused as a "constant multiple", which may block a legitimate whole-tensor ablation.
- **Fix:** if the rule matters, test whether the edit is close to a scalar multiple (e.g. `‖t − c·W‖/‖W‖ < 1e-3`).
  Decide explicitly whether to allow c=0.

### m7. Counter semantics differ from the docs
- **Where:** `driver.py:269`, `driver.py:240-244`.
- **Problems (verified by reading):**
  - The nudge check uses `>`, so the run stops on the **4th** reply in a row without a block, while the
    message says "3".
  - `refusals` is never reset, so three refusals spread over the whole run stop it. The docs describe
    "stop after 3" like the "in a row" failures.
- **Fix:** use `>=`, and reset `refusals` after a successful turn, or document that the count is cumulative.

### m8. The driver's own memory is unbounded and the kernel guard can overshoot
- **Where:** `edit.py:44-55`, `forward.py:241-249, 295-317`, `kernel.py:108-117`.
- **Problems (verified by reading):**
  - `read_staged` loads every `.pt` under `work/edited/tensors/` into the driver before checking names or
    shapes. The editor can stage arbitrarily large files: `.float()` on float16 doubles them, then a
    `deepcopy` follows.
  - Teacher-forced arrays are held twice (`parts` + `np.concatenate`), up to about 1.5 GB per model at the
    768 MB cap, on top of the 2 GB kernel.
  - The kernel RSS is polled every 0.5 s and excludes compressed memory, so a fast allocation can overshoot.
- **Fix:** check file sizes, and load with `mmap=True` after checking the name against `target`. Write
  captures straight into a preallocated `np.lib.format.open_memmap`. Use `phys_footprint` or `memory_full_info`.

### m9. The base-eval cache is keyed only on `n_per`, and dry runs rewrite a tracked file
- **Where:** `driver.py:395`, `evaluate.py:154-162`.
- **Problems:** the cache ignores which checkpoint it was computed from. The 07:47 dry run rewrote the
  tracked `runs/phase3/base_eval_n20.json` (`git status`: M).
- **Fix:** key the cache on a sha256 of `base.pt` plus the eval code version, and write dry-run caches outside the repo.

### m10. An isolation breach still produces a scored result
- **Where:** `driver.py:200-203`, `finalize`.
- **Problem:** when Codex reports a tool item, the run stops, but the edit is still evaluated and published
  with an ordinary-looking `hidden_eval`.
- **Fix:** set `result["void"] = True` for `isolation:` stops, and stop `overnight.sh` from releasing them.

### m11. overnight.sh git hazards
- **Where:** `overnight.sh:28-32`.
- **Problems (verified by reading):**
  - `git pull --rebase --autostash` runs while the tracked `runs/memwatch.log` may be written: this is the
    LOGBOOK's own lesson.
  - A failed rebase only logs the error, then `commit` runs during a rebase in progress.
  - `git commit` without paths commits whatever else is staged in the index.
  - `uv run` may re-sync the venv between pilots.
- **Fix:** untrack `runs/memwatch.log`. Run `git commit -- runs/phase3/$id`. Abort the chain if the pull
  fails. Use `uv run --frozen --no-sync`.
